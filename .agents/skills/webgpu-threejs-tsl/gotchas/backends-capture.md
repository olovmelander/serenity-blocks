# The WebGL2 backend, captures and packaging

Read before capturing a theme (playground, headless, real game), when a capture is black or blank, and when something works on WebGPU and fails on the WebGL2 backend or in the packaged app.

**Both backends are player surfaces** (ADR-0019, ADR-0008): every theme is captured on WebGPU and with `forceWebGL=1`, and the WebGL2 capture is taken on real hardware when a ray march is involved (SwiftShader hides ANGLE's faults). A Node shader gate (`tests/unit/<id>-shaders.test.js`) builds every material through both `WGSLNodeBuilder` and `GLSLNodeBuilder` and catches most backend-only build failures before a browser does. When the `chrome-devtools` MCP says "The browser is already running", another session holds its one shared profile: do not close it, capture with `node .claude/skills/webgpu-threejs-tsl/scripts/shot.mjs out.png "<url>" [width height]` (a private headless Chrome on real WebGPU; it prints the backend and the console, and exits 1 unless both are clean).

One gotcha per line; the number is the row's permanent id (cited elsewhere as "gotcha #NN"). Rows numbered below 300 were numbered before these files existed and keep their numbers, in no order. A NEW row goes at the END of this table and takes the next free number in **1200–1299**. To search: `node .claude/skills/webgpu-threejs-tsl/scripts/gotcha.mjs <words>` (`README.md` in this folder).

| #216 | A ray-march renders correctly on WebGPU and on SwiftShader but on WebGL2 on real hardware (Windows, ANGLE's D3D11 path) part of the volume vanishes and the rest smears | A small loop nested inside the march (the sample and its light taps through one inner loop, `break` on empty ash, a vec3 written by `select` per index) is mistranslated or miscompiled on that path | Keep one march loop with the taps written inline (pinned with `.toVar()`), and capture the WebGL2 backend on the real GPU (`forceWebGL=1`), not only SwiftShader. Found on Pyrestorm's plume (2026-10-13) |
| #254 | A ray-marched volume on the WebGL2 backend is washed in the colours of the event lights it holds (a lavender veil over a teal canyon once hoops are on the course), while WebGPU draws the same frame clean; the uniform table, its live count and the same loop run on its own all read identically on both | The lights were a `Loop` over a uniform table NESTED inside the march loop, which ANGLE's D3D11 path computes differently (the Pyrestorm row above is the same family: there part of the volume vanished) | Unroll the slots in JavaScript (a handful of lights) and put each behind `If(count.greaterThan(k))` (uniform across the pass, so idle slots cost nothing), leaving the march the shader's only loop; assert that in a shader gate (`for` count of the dumped fragment). Without SwiftShader's Vulkan ICD opted in, Dawn drops the device as soon as work is submitted; and Chromium 141 implements the pre-final IDL of `GPUTextureViewDescriptor.swizzle` (a dictionary) while three r186 sends the final spec's string `'rgba'` | Launch with `--enable-unsafe-webgpu --enable-unsafe-swiftshader --use-vulkan=swiftshader --enable-features=Vulkan --use-angle=swiftshader --use-webgpu-adapter=swiftshader --disable-gpu-watchdog`, and in the capture harness only (never in the repo) install an init script that strips an identity `swizzle` string before `GPUTexture.prototype.createView`. | #241 | A playground capture of a heavy scene is a uniform near-black frame with no console error, while the lowest tier (no post) and the WebGL2 backend draw | Nothing is wrong: the default tier's pipelines (a traced crystal, a reflector, the post chain) take several seconds to create on first use, and the canvas has not presented a frame yet when a sub-second capture fires. | #117 | A part captured alone (`parts=stars&noPost=1`) is a black frame though it draws thousands of quads, with no error | Every additive part writes `vec4(rgb, 0)`, so the target's alpha stays 0; with no opaque part and no post pass the canvas is fully transparent and the capture shows the page behind it | Keep one opaque part in the frame (`parts=sky,stars`) or leave the post on. Found on Galaxy (2026-10-08) |
| #79 | Works in dev, black in packaged Electron | Absolute `/assets/...` fetch resolves to filesystem root under `file://` | Use relative `./assets/...` |
| #1200 | The playground is black (or silently wrong) for EVERY effect, and the console logs `THREE.TSL: No stack defined for assign operation` from theme helpers, or `Cannot read properties of null (reading 'If')` from FXAA's build; a hard reload changes nothing | The dev server is serving two copies of three. Another worktree's dev server re-optimised the shared `node_modules/.vite` cache under it: the cache's `_metadata.json` hash no longer matches the `?v=` it serves, some dependency chunks are loaded with and without `?v=`, and each copy of three's TSL core has its own current stack | It is not a theme bug: the same code is clean on a fresh server. Confirm with `performance.getEntriesByType('resource')` (a deps chunk listed under two URLs). Do not restart the other session's server; start your own with its own cache, `VITE_CACHE_DIR=<scratch>/vite-cache npx vite --port <free port> --strictPort` (`vite.config.js` reads `VITE_CACHE_DIR`), and distrust captures taken on the bad server. Found 2026-10-20 on the shared server at port 5173; a private server on its own cache is also what every capture in a sibling worktree should use |
| #1201 | One frame in the middle of a batch of headless captures is a blank page reading `booting…`, or is drawn at another size with the card in the wrong place; the batch's console is clean and a second run of the same URL is fine | A file inside the repository was written while the batch ran (a test file, a doc, an `eslint --fix`): the dev server answers any change under its root with a full reload of every open page, and the capture took its screenshot of the page starting again | While a batch runs, write only outside the repository (the scratchpad), and apply the edits when it has finished; or serve captures from a detached worktree nothing else writes to. Seen 2026-11-16 capturing Halcyon Apex's fly-bys with a private Vite on its own port and `.claude/skills/webgpu-threejs-tsl/scripts/shot.mjs`-style CDP captures: a unit test saved mid-batch cost two frames of a strip. |
| #1202 | A capture batch comes back as frames of a few kilobytes each (blank white) while its log says every page was ready; or a script that drives the real game hangs for minutes with no output at all | The blank frames are #1201's reload under the batch; the script never noticed because it trusted `__PLAYGROUND_READY__` alone. The hang: a `Runtime.evaluate` sent while the whole game is still loading on a cold dependency cache waited minutes for its answer, and the script's log went through a pipe into `tail`, which prints nothing until the end | Ask the page's own state with the flag (`__PLAYGROUND_READY__ === true && location.search.length > 8 && !!document.querySelector('canvas')`), race every `Runtime.evaluate` against a timeout, write the log to a file as it goes, and read a batch's file sizes before its pictures (a blank 1280 × 720 PNG is about 5 KB). Keeping the batch from being reloaded at all is #1201. Found on Verdant Hills' living day (2026-11-16), session scripts built on `.claude/skills/webgpu-threejs-tsl/scripts/shot.mjs` |
| #1203 | A shader-build unit test (a part's material built with a node builder and a stub renderer) hears "THREE.TSL: No stack defined for assign operation" five times for EVERY material, clean ones included, although the same materials build clean in the browser | The test imported the builders from a path under three/src/renderers (the WGSL and GLSL node builders in the source tree). That path loads three's source modules beside the built `three/webgpu` bundle the theme imports: two copies of the TSL core, each with its own current stack, so every `assign` a material's setup makes finds no stack (the fault a dev server that serves two threes shows, met in a test) | Take the builders from the bundle the code under test uses: `THREE.WGSLNodeBuilder` and `THREE.GLSLNodeBuilder` are exports of `three/webgpu`. With `build()` from `tests/unit/helpers/tsl-node-build.js` the list of what it heard is then empty for a clean material, and a real warning stands out. `tests/unit/neon-district-dragon.test.js` (the test that builds the dragon and the event effects to WGSL and GLSL) |
| #1204 | Two captures of one playground view a second apart differ along EVERY edge of the scene (a mean of seven to eleven levels over the frame), so their difference cannot show whether a moving part (trees in wind, a flock, a shimmer) is calm or sparkles | The rest camera breathes (`applyCameraBreath`): the whole picture moves by a fraction of a pixel between the two times, and every edge lights up in the difference. The post's grain adds a floor of about one level | Take motion checks with `reduce=1` (reduced motion stands the camera still, while closed-form motion on the GPU that the theme does not gate runs on) or through a `look=` lens, which does not breathe; then only what moves differs. Compare three frames a second apart for the motion's size, and two frames one step apart (`t=10` and `t=10.033`) for sparkle: a pixel that steps by a quarter of the local contrast is one MSAA sample crossing an outline, and many of those from motion finer than a pixel is a flicker to remove (#1611). Found on Painted Ages' poplars (2026-11-20): the same crop went from a mean difference of 6.6 to 1.1 with the breath off, and the trees were then the only thing in it. `createPoplars` in `src/themes/painted-ages/painted-ages-life.js` |
| #1205 | An edit made by a SCRIPT (a patch tool, `sed -i`, a merge) is on disk and the playground reloads with a clean console, yet the capture shows the old behaviour: a new uniform reads as its default, a new entry is missing from `diagnostics()`, while other files edited in the same batch DID change | On this Windows machine Vite's file watcher can miss a write when several files are rewritten in quick succession: the dev server keeps serving its cached transform of the missed module (a fresh browser profile does not help, the stale copy is the server's). `curl -s http://localhost:<port>/src/themes/<id>/<file>.js` piped to `grep -c <a name the edit added>` printing 0 is the proof | After any scripted multi-file edit, `touch` every edited file (the theme's whole folder is simplest) before capturing; and when a capture contradicts the code, ask the server for the module before doubting the shader. Painted Ages living pass (2026-11-20): the first captures of the weather showed nothing of it until the world module was touched |
| #1206 | A batch of playground captures through one headless Chrome over CDP stops after its first frame and never ends (no error, no timeout), though every URL in it renders alone | A source file was saved while the batch ran: the dev server sent a full page reload, and a CDP call made against the page caught mid-reload (`Runtime.evaluate`, `Page.captureScreenshot`) never answered. The script awaited it for ever; its only timeout was the whole run's | Give every CDP call its own timeout that resolves with a marker (45 s is plenty), bound the wait for `__PLAYGROUND_READY__` per job, print each job's line as it finishes so a stall names its job, and do not save source files while a batch is running. When a frame in a batch stalls, capture that one URL alone with the skill's `scripts/shot.mjs` before suspecting the theme (2026-11-20) |
| #1207 | Every capture of a batch reports NOT READY with an empty console and no backend, though the same URLs rendered minutes before and nothing in the theme changed | The private dev server was dead: adding a gotcha row refreshes the skill's mirror by deleting `.agents/skills/webgpu-threejs-tsl` and copying it again, and Vite's watcher, which watches the whole repo, threw `EBUSY: resource busy or locked, watch …` on a file caught mid-delete and crashed its file watcher and the process with it. A page that never loads has no console to report | Before blaming the theme, check the port (`netstat -ano` for a LISTENING line) and the tail of the server's log. Refresh the mirror only when no dev server of yours is running (do the skill's rows after the last capture), or restart the server afterwards; a capture script should print the navigation's own failure (`Page.navigate` returns `errorText`) instead of waiting for a ready flag that cannot come (2026-11-20) |
| #1208 | In a cloud container with no GPU, headless Chromium reports a SwiftShader WebGPU adapter and the game boots, but the first presented frame kills the device: `WebGPU device destroyed`, `Instance dropped in popErrorScope`, every later `createBuffer` throws `size (…) is too large for the implementation when mappedAtCreation == true`, the WebGL contexts are lost with it, and the Odyssey world reports it could not be built. A bare `getContext('webgpu')` page that only clears does the same | The headless browser (the headless shell, and full Chromium's new headless mode alike, with or without `--use-vulkan=swiftshader`) has no shared-image backing for a WebGPU swap-chain texture on this software stack: the GPU log reads `Could not find SharedImageBackingFactory with params: usage: …WebgpuSwapChainTexture…` then `SharedImageStub: Unable to create shared image`, and the GPU process is torn down. The GPU watchdog is not the cause | Run the browser HEADED under a virtual display: `xvfb-run -a -s "-screen 0 1920x1080x24" node capture.cjs` with Playwright `headless: false` and `--enable-unsafe-webgpu --enable-unsafe-swiftshader --use-vulkan=swiftshader --enable-features=Vulkan --use-angle=swiftshader --use-webgpu-adapter=swiftshader --disable-gpu-watchdog`. Found capturing the Odyssey land for the ground, grass and trees pass (2026-11-22) |
| #1209 | A long headless capture batch of the real game stops part-way: the frame counter goes negative, the game's handles are undefined (`Cannot read properties of undefined (reading 'nodeManager')`), and the frames already written are fine | The dev server had stopped and come back (a background-task time limit ended it, and it was started again).
