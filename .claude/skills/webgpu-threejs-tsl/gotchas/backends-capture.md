# The WebGL2 backend, captures and packaging

Read before capturing a theme (playground, headless, real game), when a capture is black or blank, and when something works on WebGPU and fails on the WebGL2 backend or in the packaged app.

**Both backends are player surfaces** (ADR-0019, ADR-0008): every theme is captured on WebGPU and with `forceWebGL=1`, and the WebGL2 capture is taken on real hardware when a ray march is involved (SwiftShader hides ANGLE's faults). A Node shader gate (`tests/unit/<id>-shaders.test.js`) builds every material through both `WGSLNodeBuilder` and `GLSLNodeBuilder` and catches most backend-only build failures before a browser does. When the `chrome-devtools` MCP says "The browser is already running", another session holds its one shared profile: do not close it, capture with `node .claude/skills/webgpu-threejs-tsl/scripts/shot.mjs out.png "<url>" [width height]` (a private headless Chrome on real WebGPU; it prints the backend and the console, and exits 1 unless both are clean).

One gotcha per line; the number is the row's permanent id (cited elsewhere as "gotcha #NN"). Rows numbered below 300 were numbered before these files existed and keep their numbers, in no order. A NEW row goes at the END of this table and takes the next free number in **1200–1299**. To search: `node .claude/skills/webgpu-threejs-tsl/scripts/gotcha.mjs <words>` (`README.md` in this folder).

| # | Symptom | Cause | Fix |
|---|---|---|---|
| #216 | A ray-march renders correctly on WebGPU and on SwiftShader but on WebGL2 on real hardware (Windows, ANGLE's D3D11 path) part of the volume vanishes and the rest smears | A small loop nested inside the march (the sample and its light taps through one inner loop, `break` on empty ash, a vec3 written by `select` per index) is mistranslated or miscompiled on that path | Keep one march loop with the taps written inline (pinned with `.toVar()`), and capture the WebGL2 backend on the real GPU (`forceWebGL=1`), not only SwiftShader. Found on Pyrestorm's plume (2026-10-13) |
| #254 | A ray-marched volume on the WebGL2 backend is washed in the colours of the event lights it holds (a lavender veil over a teal canyon once hoops are on the course), while WebGPU draws the same frame clean; the uniform table, its live count and the same loop run on its own all read identically on both | The lights were a `Loop` over a uniform table NESTED inside the march loop, which ANGLE's D3D11 path computes differently (the Pyrestorm row above is the same family: there part of the volume vanished) | Unroll the slots in JavaScript (a handful of lights) and put each behind `If(count.greaterThan(k))` (uniform across the pass, so idle slots cost nothing), leaving the march the shader's only loop; assert that in a shader gate (`for` count of the dumped fragment). Stellar Velocity's second pass (2026-10-21), the hoop and front light in `stellar-velocity-nebula.js`, `tests/unit/stellar-velocity-shaders.test.js` |
| #168 | Headless Chromium (Playwright, no GPU, a cloud container) reports a WebGPU adapter, but the playground's canvas stays blank: `WebGPU Device Lost: A valid external Instance reference no longer exists` right after the first frame — or, earlier, `TypeError: The provided value is not of type 'GPUTextureComponentSwizzle'` from `_getRenderPassDescriptor` | Two separate things. Without SwiftShader's Vulkan ICD opted in, Dawn drops the device as soon as work is submitted; and Chromium 141 implements the pre-final IDL of `GPUTextureViewDescriptor.swizzle` (a dictionary) while three r186 sends the final spec's string `'rgba'` | Launch with `--enable-unsafe-webgpu --enable-unsafe-swiftshader --use-vulkan=swiftshader --enable-features=Vulkan --use-angle=swiftshader --use-webgpu-adapter=swiftshader --disable-gpu-watchdog`, and in the capture harness only (never in the repo) install an init script that strips an identity `swizzle` string before `GPUTexture.prototype.createView`. A software frame then takes 5–40 s; the WebGL2 backend (`?forceWebGL=1`) works without either fix. Found building Moonlit Greenhouse in a cloud session without the chrome-devtools MCP (2026-10-11) |
| #241 | A playground capture of a heavy scene is a uniform near-black frame with no console error, while the lowest tier (no post) and the WebGL2 backend draw | Nothing is wrong: the default tier's pipelines (a traced crystal, a reflector, the post chain) take several seconds to create on first use, and the canvas has not presented a frame yet when a sub-second capture fires. It looks exactly like a NaN poisoning the bloom chain | Before bisecting, capture again with a long settle (8 s): Crystal Cave at High needs it on an RTX 5080 Laptop. Found 2026-10-20 |
| #117 | A part captured alone (`parts=stars&noPost=1`) is a black frame though it draws thousands of quads, with no error | Every additive part writes `vec4(rgb, 0)`, so the target's alpha stays 0; with no opaque part and no post pass the canvas is fully transparent and the capture shows the page behind it | Keep one opaque part in the frame (`parts=sky,stars`) or leave the post on. Found on Galaxy (2026-10-08) |
| #79 | Works in dev, black in packaged Electron | Absolute `/assets/...` fetch resolves to filesystem root under `file://` | Use relative `./assets/...` |
| #1200 | The playground is black (or silently wrong) for EVERY effect, and the console logs `THREE.TSL: No stack defined for assign operation` from theme helpers, or `Cannot read properties of null (reading 'If')` from FXAA's build; a hard reload changes nothing | The dev server is serving two copies of three. Another worktree's dev server re-optimised the shared `node_modules/.vite` cache under it: the cache's `_metadata.json` hash no longer matches the `?v=` it serves, some dependency chunks are loaded with and without `?v=`, and each copy of three's TSL core has its own current stack | It is not a theme bug: the same code is clean on a fresh server. Confirm with `performance.getEntriesByType('resource')` (a deps chunk listed under two URLs). Do not restart the other session's server; start your own with its own cache, `VITE_CACHE_DIR=<scratch>/vite-cache npx vite --port <free port> --strictPort` (`vite.config.js` reads `VITE_CACHE_DIR`), and distrust captures taken on the bad server. Found 2026-10-20 on the shared server at port 5173; a private server on its own cache is also what every capture in a sibling worktree should use |
