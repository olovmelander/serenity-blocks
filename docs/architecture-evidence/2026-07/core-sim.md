## 1. Where the plan is stale or wrong (headline corrections)

1. **The "DAS on its own wall clock" story is half-stale.** Since a "Phase 3" change, `updateGame` advances keyboard DAS with the *authoritative sim delta* (`game.js:1133-1139`: `window.inputController.updateDAS(delta)` gated on `suppressExternalInput/isReplay/isSeeking`). The clock is unified; what remains un-fixed is that DAS *state* still lives on the `InputController` singleton (`controls.js:36-44`), is not tick-quantized, and is not in the demo snapshot. Plan 5.3's wording should change from "move DAS onto the sim clock" (done) to "quantize + snapshot the DAS accumulators" (not done).

2. **The gamepad DAS advance in the live single-board path is dead code.** `game.js:1140-1141` calls `window.gamepadController.advanceGameplayInput(safeTime)` — but **`window.gamepadController` is never assigned anywhere in `src/`** (only `this.gamepadController = new GamepadController()` at `main.js:2482`; the sole `window.*` input assignment is `window.inputController` at `main.js:3509`). `processDasTimers` (the only gamepad held-repeat driver, `gamepad-controller.js:1682-1755`) is reachable only via `advanceGameplayInput` (`gamepad-controller.js:440-451`), whose live call sites are: legacy fallback loops `main.js:4810/4860`, and `OnlineMultiplayerMode.js:2791`. `LocalMultiplayerMode`'s loop advances keyboard DAS only (`LocalMultiplayerMode.js:789-791`). Consequence: gamepad hold-to-repeat (left/right/soft-drop) is advanced **nowhere** in SinglePlayer/Infinity/Odyssey/Local-MP live paths — initial presses fire from the poll loop (`gamepad-controller.js:1544-1585`) but `startDas` timers never tick. This is stronger than the review §2.8 claim ("second, independently-clocked copy... on its own RAF poll loop" — the poll loop does *not* advance DAS at all) and stronger than plan 5.4 ("wire gamepad advance into the local-MP loop" — it needs wiring into *every* live loop, or the one-word fix `window.gamepadController = this.gamepadController`). Needs a 2-minute manual pad-hold smoke to confirm user-visible breakage, but the call graph is conclusive.

3. **A latent DAS double-advance exists in the legacy fallback path.** `main.js` `gameLoop` (4804) calls `this.inputController.update(currentTime)` (4809, advances DAS by wall delta) *and then* `coreGameLoop → updateGame → window.inputController.updateDAS(delta)` (`game.js:1138`) — 2× DAS rate whenever the legacy path runs. It is reachable only via the catch-fallback at `main.js:4329-4341`, but plan 5.5's loop collapse should explicitly delete `main.js:4804-4892` rather than "collapse" them.

4. **Plan 5.6's "existing `getState`/`setState` seam" only exists on one of TWO duplicated LCGs.** `seededRandom` (`src/utils/helpers.js:21-37`) has the seam and is used by demo record/replay and local-MP shared seeds. But FFA online MP uses its own inline copy, `createSeededRNG` (`ffa-p2p-game-state.js:2178-2185`, same 9301/49297/233280 constants) **without** `getState`/`setState` or `.seed`. Swapping the PRNG "behind the seam" misses the online path; step 5.6 needs a "unify the two LCG copies first" sub-step.

5. **Plan 5.3 ignores that a fixed-tick accumulator already exists in the netcode layer.** Default-off `simTickNetcode` gives the FFA host a 60 Hz tick accumulator (`ffa-p2p-game-state.js:374-377, 455-476`, driven at `3850-3854`, with `unifiedLoop.setExternalPlayerUpdate` at `3831`). Phase 5's fixed-tick core should subsume/replace this flag, not duplicate it — the plan never mentions it in Phase 5 (only Phase 6's flag-graduation table).

6. **The Phase 1 band-aid → Phase 5 link is already implemented as prescribed.** The host double-apply fix buffers-only and carries the exact comment the sequencing notes demanded: `ffa-p2p-game-state.js:1589-1591` ("temporary correctness fix. The structural fix is tick-boundary input application... see docs/ARCHITECTURAL_REMEDIATION_PLAN.md Phase 5"). The plan can mark that sequencing note "done".

7. **Phase 2 leftover confirmed:** the live 15-lines/level progression is inside the cascade loop at `physics.js:794-804`, seeded by `linesUntilNextLevel = 15` (`game.js:389, 503`; restore default at `demo-state.js:140`). `scoring.js:61-69` carries the single-source warning comment. The plan's "decide whether to extract now or leave the comment" should be resolved: **fold it into 5.2's `resolveCascade` signature** (it is inherently part of the lock resolution result), don't extract twice.

## 2. Phase 5 step-by-step feasibility against today's code

### 5.1 GameState read/write boundary (M) — accurate but under-specified
The plan gives no shape for the boundary. Evidence for the design: the board is represented three coherent-by-hand ways (`lockedPieces` / `boardGrid` / `boardCache` + `boardCacheDirty`, kept in sync via `ensureBoardCache` game.js:65-87, `markBoardDirty` game.js:319-327, `rebuildBoardGridFromPieces` per-lock at game.js:1025 and per-cascade-iteration at physics.js:672/857/909/976). A practical boundary is *not* getters/setters over 62 fields; it is: (a) make `lockedPieces`→`boardGrid`→`boardCache` derivation one-directional behind 3-4 mutation methods (`lock`, `clearLines`, `applyGarbage`, `restore`), (b) route the 22 FFA write sites through them. Risk the plan omits: `demo-state.js` `restoreGameStateSnapshot` (113-221) and FFA `_applySnapshotState` both bulk-assign fields — the boundary must include a sanctioned bulk-restore or those two become permanent bypasses.

### 5.2 Pure `resolveCascade` (L) — feasible; the plan understates what will fight back
The seams are real: `lockPiece` is the **single** entry to physics (`game.js:1031-1066` sets `isProcessingPhysics`, calls `processPhysics`, chains `spawnPiece`), and `cascade-simulator.js` proves the loop extracts (pure `resolveCascadeAfterstate` recursion, `cascade-simulator.js:214-250`).

What the plan does not say:

- **`cascade-simulator.js` is NOT rules-parity — it is a bot heuristic.** Its wave scoring is `scoreCascadeWave` (`cascade-simulator.js:203-212`: `linePower × chainPower`), not `calculateQuadraLineScore` (`scoring.js:23-59`); it has **no level progression, no B2B/T-spin, no hole-mask computation, no `movedArray`**. Its component flood-fill uses `stack.pop()` (already O(1), `cascade-simulator.js:70-99`) while the live `findConnectedComponents` uses `queue.shift()` (`physics.js:118` — the O(n²) target of 5.2 is confirmed present). "Modeled on" is right; "reuse" would be wrong. Budget for building hole-mask parity (physics.js:645-765 `movedArray` + `buildHoleMaskRows` semantics) into the pure core — that's the Quadra-critical garbage payload, and it is the hardest part to make pure because `movedArray` is threaded through `applyGravity` (`physics.js:185-323`).
- **The animation-replay contract is 18 callbacks wide and unspecified.** `processPhysics` fires: `triggerCombo`, `triggerCascadeWave` (physics.js:688-695), `onLineClear` (819-826), `playLineClear`, `onScoreAdd` (816-817), `onLevelUp`/`playLevelUp`/`updateBackground` (799-807), `onTSpin`/`onB2B` (829-843), `onLineClearImpact`/`triggerFlash`/`triggerBackgroundPulse` (845-847), `updateBoard`+`draw` ×3 flash stages (877-903), `onGravityStep` (307), `onCascadeComplete` (928-930), `onPerfectClear` (940), `onGarbageReady` (947-964), plus `onPieceLock`/`onHardDrop` from game.js. "Drive animation as a replay of precomputed waves" requires a written schedule of *which callback fires at which wave/sim-time with which payload* — otherwise every theme/juice consumer (55 theme files per the review) silently breaks. This deliverable is missing from the plan.
- **Mid-cascade side-effect ordering is observable state.** Score and level mutate *per wave inside the loop* (`physics.js:791-814`) and MP snapshots broadcast at 30 Hz can capture mid-cascade values. A pure resolver that commits score/level once at the end changes wire-visible timing. The plan needs an explicit decision: commit-per-wave (replaying waves mutates incrementally) or commit-at-end (accept snapshot-timing change and pin with a test).
- **The replay clock is advanced inside the animation delays.** `waitForPhysicsDelay` → `advanceReplaySimulationClock` (`physics.js:44-70`) is how replays keep `simTimeMs` honest across the 70 ms fades and 16 ms gravity steps. Extracting the pure core must preserve *deterministic* sim-time consumption per wave, or every existing demo's input `t` values misalign. Abort criterion: golden demos (`tests/unit/demo-replay-clock.test.js`, 17 cases; `ffa-demo-replay-determinism.test.js`) must stay green through the extraction.

### 5.3 Fixed-tick sim (L) — 70-80% built, but the remaining 20% is in five scattered places
`simTickMs/simTimeMs/simFrame` exist (`game.js:403-405`) but `simFrame` is *derived by rounding* (`game.js:1118`), not stepped. `processAutoDrop` is a real fixed-step accumulator with a 32-step cap and 2×-interval clamp (`game.js:831-875`). The un-quantized remainder: DAS accumulators (controls.js:123-155 — float ms, live `window.settings` reads per call at controls.js:77-80), lock-delay timer (`lockTimer += delta`, game.js:207-209), hit-stop (decremented in **three** places: game.js:1120-1121, unified-game-loop.js:195-197, LocalMultiplayerMode.js:827-829), blind timers (`delta/1000` seconds at LocalMultiplayerMode.js:824 and unified-game-loop.js:192), and the lock bonus (float `framesElapsed` division, game.js:940-946 — already sim-time-based via `getGameplayTimeMs` game.js:238-246, good). Also note delta-clamp asymmetry that breaks cross-fps identity today: `InputController.update` clamps at 100 ms (controls.js:65), `updateGame` doesn't clamp at all (game.js:1109), `advanceGameplayInput` clamps at 100 ms (gamepad-controller.js:442).

### 5.4 Unify DAS engines (M) — right idea, wrong wiring description
The two engines are near-identical math (controls.js:111-173 vs gamepad-controller.js:1682-1755) but differ in config source: keyboard reads `window.settings.dasDelay/dasInterval` live every frame; gamepad caches `this.dasDelay=120/this.dasInterval=40` (gamepad-controller.js:130-131) updated only via `updateDasSettings` from `main.js:3988-3993, 4237-4243`. A shared `advanceDas(state, ticks, config)` must pick one config-propagation model. Moving DAS state into `GameState` will break: `pauseGame/resumeGame` clearTimers calls (`game.js:1275-1277, 1288-1291`), the visibilitychange clear (`controls.js:546-553`), `main.js:4795-4796` resume clears, and the P2 keyboard slots (`p2_*` in the same singleton, controls.js:41-43) which belong to a *different* player's GameState in local MP — the plan should specify per-player DAS state keyed into each `GameState`, with the singleton reduced to key→edge detection.

### 5.5 Collapse the loops (M) — the count is bigger than "3 (+ hybrid)"
Live sim-loop implementations today: (1) recursive `gameLoop` (`game.js:1180-1223`) used by SinglePlayerMode:753, InfinityMode:761, OdysseyMode:2669; (2) `FrameRateController` hybrid setTimeout+rAF (`frame-rate-controller.js:288-441`) used by the *same three modes* when targetFPS > monitor Hz (SinglePlayerMode:724-747, InfinityMode:736-756, OdysseyMode:2644-2664); (3) `LocalMultiplayerMode._startGameLoop` rAF (`LocalMultiplayerMode.js:754-870`, calls `processAutoDrop` directly, bypassing `updateGame` — so hit-stop/blind/DAS logic is re-implemented inline); (4) `UnifiedMultiplayerLoop` (`unified-game-loop.js:134-213`); (5) `DemoPlayer`'s own frame loop (`DemoPlayer.js:230-277`); plus two **legacy fallback** loops `main.js:4804/4852` (reachable only via the catch at main.js:4329-4341) and the gamepad poll rAF (`gamepad-controller.js:379-385`, input sampling only). `MAX_CONCURRENT_LOOPS = 2` band-aid confirmed at `game.js:1070-1071, 1189-1194`, reset in `startGame` at 1245. **New since the review:** `UnifiedMultiplayerLoop.neverPause` latch (unified-game-loop.js:22-25, 101-119, set at ffa:4467) — competitive-MP must never pause; the consolidated runner must carry this policy or online MP regresses. The plan should also state that consolidation removes the LocalMultiplayerMode inline re-implementations (hot-potato/hit-stop/blind handling at LMM:771-830) into the shared runner.

### 5.6 PRNG + delete checkpoints (M) — two unstated costs
Besides the dual-LCG issue (§1.4): (a) **checkpoints serve seek, not just correctness.** `DemoPlayer._findCheckpoint` (511-526) + `_captureRuntimeCheckpoint` (471-495) make scrubbing O(300 frames); pure-input replay makes a seek to minute 10 an O(full-resim) operation with `await`s per lock (`_waitForPhysics` DemoPlayer.js:402-419). The plan should replace "delete the full-state checkpoint machinery" with "demote checkpoints to *derived seek keyframes* (never authoritative)" — same trust win, no UX regression. (b) **Seed sources are wall-clock/Math.random:** `Date.now()` at SinglePlayerMode.js:292, `Math.floor(Math.random()*1e6)` at ffa:2055, and `randomGenerator` *defaults to `Math.random`* (`game.js:379, 498`) — casual unseeded play exists; the 5.7 artifact requires always-seeded starts. Old demos: RNG swap changes the bag stream, so 5.8's sim-version gate must version the *RNG algorithm and bag* specifically (the current `rulesVersion` field is a placeholder — it's just set to `DEMO_VERSION` at DemoRecorder.js:66).

### 5.7 Canonical match artifact (M) — the current format, measured
Today's demo v2 records (`DemoRecorder.js:52-71`): `version:'2.0'`, `gameMode`, `timestamp`, `sim{tickMs, startFrame, durationFrames}`, `initialState{seed, level, dropInterval, settings, rulesVersion}`, `inputs[{f, t, a, d?, q?}]` (frame-indexed accepted commands, `q` = buffered during physics), `checkpoints[{f, t, inputIndex, state}]` at ≥300-frame cadence (`DEMO_CHECKPOINT_INTERVAL_FRAMES = 300`, DemoRecorder.js:10) only at *stable* states (no mid-physics; `isStableDemoCheckpointState` demo-state.js:30-35), and `metadata`. The full-state checkpoint snapshot is ~40 fields incl. `boardGrid`, `lockedPieces`, `rngState`, `pieceIdCounter` (demo-state.js:44-111). **Bug found:** `_captureSettings` records `settings.das`/`settings.arr` (`DemoRecorder.js:205-211`) but the real keys are `dasDelay`/`dasInterval` (`ui/settings.js:12`, `constants.js:226`) — the captured input-timing settings are always `undefined`. Harmless today (only discrete accepted commands are replayed) but it proves nobody has ever consumed those fields; 5.7 should define them properly or drop them. Missing vs the plan's target artifact: no per-lock/periodic digests, no authoritative-event stream, no final summary digest, no real `simVersion`. Storage is IndexedDB + gzip-base64 URL export (`DemoManager.js`), no schema validation on import beyond `version && inputs` (DemoManager.js:148-159).

### 5.9 Determinism soak tests (M) — a foundation exists
Already present: `tests/unit/ffa-demo-replay-determinism.test.js` (seed → byte-identical board/piece sequence, 4 cases), `demo-replay-clock.test.js` (17 cases: v1→v2 normalization, checkpoint stability, RNG-state restore, sim-time lock bonus), `demo-piece-id-counter.test.js`, `src/core/__tests__/replay-proof.test.js` (note: `buildReplayProof` is **shape-only** — seed present + monotonic input log; it does not re-simulate). Missing exactly what 5.9 says: same input stream at 30/60/144 fps with pause/resume asserting identical digests — feasible only *after* 5.3, since today `updateGame` consumes raw rAF deltas.

### 5.10 Differential cutover (M) — practical; here is the concrete tap
The tap points exist and are narrow: **pre-lock** — clone `boardGrid` + `comboState` in `lockPiece` just before `processPhysics` starts (`game.js:1031-1035`); **post-physics** — the completion `.then` (`game.js:1036-1049`) or after `rebuildBoardGridFromPieces`/`markBoardDirty` (`physics.js:976-979`), diffing board digest, `lines`, wave count, and `comboState.holeMask`. Constraints the plan omits: (a) the legacy path is *async* — the diff must await `latestPhysicsPromise`, and abort if a restart/game-over interleaves; (b) **garbage insertion is a second board mutator outside the lock path** (`insertPendingGarbage` ffa:1803-1869 → `insertGarbageEntries` mutating `lockedPieces`/`boardGrid`) — the shadow resolver must treat garbage as an input event or every MP diff false-positives; (c) score cannot be diffed against `cascade-simulator.js` as-is (heuristic scoring, §2 above) — the diff target must be the *new* `resolveCascade` built to parity, with the simulator left to the bot; (d) Infinity mode boards (up to `maxRows=1000`, game.js:366) make full-board digests per lock non-trivial — digest incrementally or hash only occupied extents.

## 3. Measurable performance stakes

- **Input dead-time during cascades (the user-facing win):** input primitives hard-return while `isProcessingPhysics` (`move` game.js:648-653, `rotate` 686-690, `softDrop` 791-795, `hardDrop` 884-889); only 4 move/rotate commands are buffered (`applyBufferedInputs` game.js:248-269; queue cap enforced at SinglePlayerMode.js:555-572), drops are discarded. Per cascade wave the animation costs 70 ms × speedMultiplier (30+20+20 at physics.js:879/891/903, multiplier 1.0→0.5 at 865-867) plus 16 ms per gravity settle step (physics.js:232, 312). A 4-wave cascade with ~8 total gravity steps ≈ **330-400 ms of blocked input**; on Infinity boards with deep cascades this exceeds a second. Post-5.2 the resolution is synchronous (sub-ms on a 240-cell grid) and input applies on the next tick — the measurable KPI is "p95 time from accepted input to sim application during cascades", from >300 ms to ≤1 tick (16.7 ms).
- **`queue.shift()` flood fill:** confirmed at `physics.js:118`; O(n²) worst-case matters only on Infinity grids (1000×10 = 10,000 cells); `findConnectedComponents` also re-allocates a `visited` matrix and per-component shape arrays every wave (physics.js:101, 151). The pure resolver should adopt cascade-simulator's stack-pop pattern (cascade-simulator.js:70) plus scratch reuse.
- **Loop consolidation:** negligible frame-time win (each loop is one rAF); the payoff is correctness (one delta-clamp policy, one pause policy, deleting the double-advance and dead branches) and the removal of `MAX_CONCURRENT_LOOPS`. Do not promise FPS from 5.5.
- **Per-lock rebuild cost:** `rebuildBoardGridFromPieces` runs at minimum twice per lock (game.js:1025, physics.js:672) and 3-4× per cascade wave (physics.js:857, 909, 976) — a free win for 5.2 to note (the pure resolver mutates one grid, no rebuilds).

## 4. Missing from Phase 5 entirely (should be added in the rewrite)

1. **Animation-replay contract deliverable** (the 18-callback schedule, §2/5.2) — without it 5.2 cannot be reviewed as "behavior preserved".
2. **Rollback/state-serialization budget.** Phase 6 wants rollback on the Phase 5 frame number, but the only serializer is `captureGameStateSnapshot` using `structuredClone` of the full board (demo-state.js:6-11, 44-111) — fine at 1/300 frames, unusable at 60 Hz. Phase 5 should deliver a compact binary savestate (or dirty-region snapshot) as an explicit artifact, or Phase 6's rollback claim is unfounded.
3. **Float hazards inventory & policy.** `dropCounter`, `simTimeMs`, DAS/lock/hit-stop accumulators are float ms with three different clamp policies (§2/5.3). The fix is integer tick counts everywhere; the plan says "whole simTickMs quanta" but doesn't ban float accumulators in snapshotted state.
4. **Determinism boundary violations via `window.*` in core.** `resolveActiveTetrominoColor` reads `window.settingsManager/themeManager` *inside the sim* (game.js:24-46) and the resulting theme color is baked into `lockedPieceSnapshot`, `comboState.sourceColor`, and garbage payloads (game.js:951-957, 997) — board cell contents differ by active theme. Phase 3d's fitness check ("no DOM/UI imports from src/core") will not catch this because it's a global read, not an import; and any board digest that hashes cell colors will desync across themed peers. Phase 5 must either exclude color from digests or move color resolution out of the sim.
5. **`isReplay` sim-time forking.** `updateGame` sets `simTimeMs = safeTime` when `isReplay` (game.js:1112-1116) vs accumulating delta otherwise — two time bases in one function; the rewrite should call for one canonical accumulation path.
6. **Always-seeded starts.** `randomGenerator` defaults to `Math.random` (game.js:379, 498) and `startGame`/`reset` re-defaults it; the 5.7 artifact silently becomes unverifiable for any mode that forgets to seed. Add "constructor requires a seed" to 5.6's exit criteria.
7. **The `updateGame`-bypass loops.** LocalMultiplayerMode and UnifiedMultiplayerLoop call `processAutoDrop` directly (LMM:857, unified-game-loop.js:206), so any logic added to `updateGame` (like the DAS advance) silently doesn't apply to MP. 5.5 should name "every mode goes through one `advanceTick`" as the exit criterion, not "one runner".
8. **Demo settings capture bug** (`das`/`arr` undefined keys, DemoRecorder.js:208-209) — one-line fix, belongs in 5.7's schema definition.

## 5. Success measurement & abort criteria (proposed, currently absent)

- **5.2:** golden-demo suite (existing demo tests + N recorded real games) replays byte-identical board/score/lines before and after; shadow-diff (5.10) clean over ≥50 sessions; abort if hole-mask parity vs Quadra tables cannot be reproduced (garbage fairness is competitive-visible).
- **5.3/5.4:** the 5.9 multi-fps soak becomes the gate: same input stream at 30/60/144 fps + pause/resume → identical `(board digest, score, garbage sequence)`; input-to-application p95 ≤ 1 tick during cascades.
- **5.5:** grep-level fitness check: exactly one `requestAnimationFrame` sim driver under `src/core/**`; `MAX_CONCURRENT_LOOPS` deleted; `neverPause` behavior pinned by a test.
- **5.6:** bag distribution χ² sanity + old-demo gate (v2 demos replay under `rulesVersion` gating or are explicitly marked legacy).
- **Perf regression guard:** cascade resolution CPU time per lock (should *drop*), and Phase 3d frame p95/p99 budgets unchanged on the heavy themes (the sim is not the GPU bottleneck; don't let 5.x churn touch render paths).
