### Context & Tech Stack
* **Game Overview:** Serenity Blocks is a Tetris-inspired stacking game with a heavy cinematic/visual layer. The core gameplay board is a 2D-style Tetris field (10x24 grid, 7-bag, SRS + legacy rotation, T-spin, cascade/Quadra line-clear physics) rendered via Phaser. Behind and around it sits an extensive 3D presentation layer: ~64 animated visual themes and a separate full-3D "Odyssey" level-select journey (8 chapter environments). Game modes are SinglePlayer, Serenity, Infinity (endless), LocalMultiplayer (local 2-player), OnlineMultiplayer/FFA (host-authoritative P2P over Steam), and Odyssey.
* **Current Core Tech:** Vanilla JavaScript ESM (no project-wide TypeScript; no root `tsconfig.json`), bundled by Vite 5, shipped as an Electron 38 desktop app with deep Steam integration (steamworks.js P2P + ez-steam-api leaderboards, native modules via koffi). Rendering is a **3-tier hybrid**: (1) Phaser 4.0.0-rc.5 (`type: Phaser.WEBGL`) draws the actual gameplay board using Graphics primitives, with raw `CanvasRenderingContext2D` helpers for next-queue/opponent panels; (2) a custom hand-written WebGL1 engine (`src/rendering/renderer.js`, class `WebGLRenderer`) drives theme particle backgrounds; (3) Three.js **r181** (`three` ^0.181.2) powers the themes and all of Odyssey, predominantly via the **WebGPU/TSL node-material pipeline** (`three/webgpu` + `three/tsl`) with automatic **WebGL2 fallback** (`?forceWebGL=1` forces it for QA). Tooling: ESLint (airbnb-base, 4-space), Prettier, Vitest 3; packaging via electron-builder (NSIS Windows, AppImage Linux).
* **Current State:** Late-stage production/scaling, solo-developer codebase (~550 source JS files, 64 themes, 49 Vitest files, 394 archived historical fix/plan docs). The shipping pipeline is fully built (NSIS + signtool config + bundled Steam native modules) but **not yet shipped**: `steam_appid.txt` is still Valve's placeholder `480` (Spacewar) and there is no release output. A large WebGPU/TSL migration of Odyssey is **already executed in the working tree but sitting uncommitted**, overlapping an active repository-cleanup branch.

* **The Odyssey WebGPU/TSL migration is effectively complete, contradicting `docs/ODYSSEY_AAA_MASTER_PLAN.md`.** That plan is written in future tense and still calls the Odyssey board "the WebGL holdout" with "~63 raw GLSL ShaderMaterials" — but on disk `OdysseyBoardController.js` already uses `new THREE.WebGPURenderer(...)` (with WebGL2 fallback + backend detection), all 8 chapters have `.tsl.js` sibling builders, the GLSL `rim-shaders.js` is deleted, and exactly **one** raw `THREE.ShaderMaterial` remains in the entire `odyssey/` tree (the nebula plane, `OdysseyBoardController.js:762`). Treat the plan doc as stale; review the working tree.
* **`?odysseyAAA=1` is now a diagnostics-overlay-only flag** — the cinematic conductor path is default-on; the flag only stamps the debug overlay (`OdysseyBoardController.js:606`).
* **The real WebGL/GLSL holdouts are elsewhere, and the theme layer is genuinely mid-migration.** `WarpTransitionRenderer.js` and the legacy `src/rendering/renderer.js` background engine remain WebGL; across the themes ~25 instantiate a `WebGPURenderer` while ~41 still build raw GLSL `ShaderMaterials` (many themes are in *both* lists, working only via the WebGL2 fallback). Codebase-wide, ~393 raw `THREE.ShaderMaterial` instantiations coexist with ~375 NodeMaterial instantiations.
* **No project-wide TypeScript.** The codebase is vanilla JS ESM with JSDoc comments and no type-checking step. The sole exception is 7 `.ts` files under `src/themes/tornado/`, imported with literal `.ts` extensions and transpiled on the fly by Vite/esbuild (no `tsc`, no `tsconfig.json`) — an isolated experiment holdout.
* **Multiplayer is host-authoritative P2P over Steam, NOT WebRTC.** Outside Electron+Steam it degrades to a `BroadcastChannel` mock for dev only. A custom 4-bit-per-cell binary protocol (`network/binary-encoding.js`) with delta encoding claims ~90% bandwidth reduction — but is then base64-wrapped inside a JSON envelope on the wire, so the claim is pre-transport. The networked stack is centralized in a ~3084-line god-class (`ffa-p2p-game-state.js`).
* **There are two parallel, unbridged event buses:** a synchronous singleton (`events/event-bus.js`) for core/theme/UI, and a separate "optimized" bus (`utils/event-optimizer.js`, wrapped by `events/multiplayer-events.js`) for multiplayer. Code listening on one silently misses the other.
* **`single-player-canvas-renderer.js` is effectively dead code** (referenced only by itself; the live single-player board is Phaser). Don't mistake it for the active renderer.

### Specific Strategic Questions to Address
* **Engine Strategy (the real question, not "Phaser v4.1.0 Salusa"):** Phaser is live but pinned to an unstable RC and confined to the 2D board. The genuine decision is twofold: (a) **stabilize or replace Phaser's role** — pin to a stable release, keep it as the dedicated 2D-board engine, or absorb the board into Three.js/canvas to collapse one GPU context; and (b) **finish the Three.js WebGPU/TSL migration** — drive the ~393 remaining raw GLSL `ShaderMaterials` (themes, `WarpTransitionRenderer`, the legacy WebGL1 background engine) to TSL so the WebGL2 fallback becomes a true fallback rather than a load-bearing path. * **Alternative Techniques & Languages:** Weigh, with concrete cost/benefit for *this* codebase:
  * **Strict TypeScript adoption** across a ~550-file vanilla-JS ESM base (incremental `checkJs`/JSDoc-types vs. a hard `.ts` migration), and what to do with the orphan `src/themes/tornado/*.ts` files.

  * **The hybrid 2D-board + 3D-Three.js model** itself — keep the split, or unify rendering under one engine for fewer contexts and simpler device-loss handling.
  * Bundling/DX wins (Vite `manualChunks` tuning, dependency-placement hygiene — `phaser` belongs in `dependencies`).
